Il file scaricato va incollato al posto del blocco GROUND_TEXTURE_CONFIG in cima a app.js, così al prossimo avvio la texture viene ricaricata già nella stessa posizione/dimensione/rotazione. Per il caricamento automatico all'avvio, il file immagine va messo nella stessa cartella di index.html con il nome indicato in GROUND_TEXTURE_CONFIG.fileName (di default ground-texture.jpg).

Traslazione e rotazione manuale

Sposta il modello PFB selezionato nella tabella qui sopra lungo i tre assi del file (le stesse frecce colorate rosso/verde/blu = X/Y/Z disegnate accanto al modello), in aggiunta alla sua posizione base (origine o rover); ruotalo su sé stesso attorno alla verticale; oppure specchialo su uno o più dei suoi assi — utile quando non sai ancora con che convenzione è orientato al proprio interno il file .pfb. Ogni spostamento viene anche stampato in console con la posizione finale x, y, z nella scena.

Livello di dettaglio (PFB)

Un file .pfb contiene molti nodi LOD indipendenti (uno per zona), ciascuno con più rappresentazioni alternative dello stesso terreno a dettaglio diverso: vanno scelte, mai unite. 0 = massimo dettaglio disponibile in ogni zona.

Esportazione

Orientamento assi (.vst)

Nei file .vst l'asse Z è convenzionalmente rivolto verso il basso e la terna non è destrorsa. Per ogni asse del file, scegli a quale asse della scena 3D corrisponde (di default: Z del file → giù nella scena). Assegnare un asse già in uso lo scambia automaticamente con quello liberato. Questa mappatura riguarda solo il terreno .vst, non i modelli .pfb (vedi le card dedicate).

Orientamento assi — posizione (.pfb)

Governa SOLO dove viene collocato il modello: la trasformazione applicata a totalOffset (site/drive, da drives.js) per calcolare la posizione "Pos. rover" e la posizione dei dischetti/paletti in scena. Non tocca la forma né l'orientamento della mesh caricata (per quello vedi la card "Orientamento assi — vertici" qui sotto): le due mappature sono indipendenti, perché la convenzione con cui è orientato il file .pfb al suo interno non è detto coincida con quella del sistema di riferimento site/drive. Assegnare un asse già in uso lo scambia automaticamente con quello liberato.

⚠ Con questa mappatura, Z del file NON è assegnato a Y (verticale) della scena: la quota reale (elevazione) del rover finirebbe mescolata a una coordinata orizzontale. Lascia sempre Z del file → Y+ oppure Y−; cambia solo l'assegnazione di X e Y.

Orientamento assi — vertici (.pfb)

Indipendente dalla mappatura "posizione" qui sopra: governa SOLO la forma/ orientamento della mesh caricata (i vertici del file, il winding delle facce e le frecce colorate X/Y/Z disegnate accanto al modello), non dove il modello viene collocato in scena. Nei tuoi file .pfb il modello è molto esteso sul piano X/Y del file e poco esteso lungo Z: perché il terreno resti "sdraiato" in piano nella scena (anziché diventare un muro verticale), Z del file va quasi sempre mappato su Y. Assegnare un asse già in uso lo scambia automaticamente con quello liberato. Per specchiare un asse SOLO di un modello specifico (senza toccare gli altri file caricati) usa i toggle "Specchia X/Y/Z" nella card "Traslazione e rotazione manuale", non questi menu (che valgono per tutti i .pfb caricati).

⚠ Con questa mappatura, Z del file NON è assegnato a Y (verticale) della scena: il modello, sottile lungo il proprio Z ed esteso su X/Y, smette di sdraiarsi in piano e diventa un muro verticale. Lascia sempre Z del file → Y+ oppure Y−; cambia solo l'assegnazione di X e Y.

Sul formato .vst

ViSTa (Visible Scalable Terrain) è il formato binario sviluppato dal JPL per il Science Activity Planner delle missioni Mars Exploration Rover (Spirit e Opportunity), per rappresentare mesh di terreno ricostruite da coppie stereo con più livelli di dettaglio.

Struttura binaria letta da questo visualizzatore
VSTHeader(40B) → BoundingBox(24B) → TextureRef[n×2048B] → CoordinateSystem(4096B) → Vertex[vertexCount×20B] → LOD[lodsCount] { LODHeader(28B), BoundingBox(24B), Patch[patchesCount] { PatchHeader(24B), IndexArrayLength[], Index[] } }

Fonte: NASA Tech Brief NPO-30600 «Format for Interchange and Display of 3D Terrain Data» (Backes, Powell, Vona, Norris, Morrison — JPL/Caltech); Vona et al., «Challenges in 3D Visualization for Mars Exploration Rover Mission Science Planning», IEEE Aerospace Conf. 2003.

Sul formato .pfb

Performer Fast Binary è il formato nativo di SGI IRIS/OpenGL Performer: una serializzazione diretta dello scene graph (nodi, geoset, geostati, materiali, texture). SGI non ha mai pubblicato una specifica byte-per-byte — il manuale ufficiale lo dichiara esplicitamente "undocumented and subject to change".

Struttura letta da questo visualizzatore
Header(16B) → blocchi taggati {LengthLists, VertexLists, ColorLists, NormalLists, TexcoordLists, Materials, Textures, GeoStates, GeoSets, Nodes} → gerarchia Group/SCS/DCS/LOD/Geode con trasformazioni 4×4 accumulate

Fonti: OpenGL Performer™ Programmer's Guide (SGI, doc. 007-1680-100) per la semantica di nodi/pfLOD/pfGeoSet; OpenPFB (J.C. Hoelt, CNRS-IRIT, LGPLv2) per la struttura dei blocchi, verificata e corretta byte per byte su file reali.
